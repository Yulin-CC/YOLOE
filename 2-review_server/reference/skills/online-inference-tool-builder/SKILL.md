# 在线推理工具开发

把算法 HTTP 服务包装成可实际使用的 Web 工具：输入可检查、过程可追踪、失败可解释、结果可恢复和复核。以 CDVIS 的轻量实现为参考模式，但不要复制其变化检测业务常量、接口地址、模型编号或视觉品牌。

## 开始前

先检查目标仓库、现有技术栈、启动方式和已有改动。若是增量开发，优先延续项目已有架构；若是新项目，再按规模选择实现档位：

- 本机或可信内网、单用户、短任务、小批量：可用静态前端 + 轻量 Python HTTP 服务 + JSON 文件持久化。
- 多用户、长任务、GPU 排队、大批量或需要断点恢复：使用服务端任务队列/worker + 数据库 + 对象存储；不要让浏览器承担任务编排。

落实需求前确认这些变量：输入数量与类型、批量配对规则、模型参数、推理接口与鉴权、输出数据形状、历史保留策略、并发规模、部署边界。用户未提供模型协议时，将其隔离成 adapter 并标出待接字段，不要臆造可工作的端点或响应。

## 实施原则

1. 先定义领域契约：`Task`、`Item`、任务状态、输入元数据、规范化结果和错误结构。UI、持久化和模型 adapter 都围绕该契约工作。
2. 浏览器默认只访问本工具后端，由后端代理模型请求、保存原始输入和规范化结果。密钥只留在服务端。
3. 将任务拆成“创建 → 逐项处理/排队 → 终结”的显式生命周期。至少区分 `running`、`completed`、`partial_failed`、`failed`；增强版再加入 `queued`、`cancelled`、`interrupted`。
4. 每个输入项独立记录状态、耗时、错误、原图引用和规范化结果。单项失败不应吞掉已成功结果，也不应伪装成整个任务成功。
5. 后端是任务状态的权威来源。前端刷新或重新打开后，应能通过任务列表与详情恢复结果视图。
6. 在服务端再次校验文件、参数、请求大小和路径；前端校验只用于即时反馈。
7. 轻量文件持久化必须使用临时文件 + 原子替换，并对同一任务加锁。出现多进程写入或复杂查询需求时切换 SQLite/数据库。
8. 批量输入必须确定性排序，显式报告未配对、重复键和不支持文件，避免静默覆盖。
9. 保存模型原始响应仅用于诊断且应可配置；业务展示依赖稳定的规范化结果，避免 UI 与供应商响应强耦合。
10. 删除任务前确认，并在服务端校验解析后的目标仍是数据根目录的直属任务目录；拒绝符号链接和路径穿越。

## 推荐工作流

1. 写出一页实现约定：输入/输出示例、任务状态转换、部署假设和验收标准。
2. 先完成一条真实纵向链路：单个输入 → adapter → 持久化 → 结果页；确认协议后再扩展批量、历史和高级查看器。
3. 将模型差异收口到 adapter，把 UI 文案、参数表单和结果 renderer 做成配置或小型注册表；不要到处分支判断模型编号。
4. 完成错误路径：模型超时、非 JSON、业务码失败、部分失败、无结果、损坏任务文件和页面刷新。
5. 根据输出类型选择结果呈现。分类/文本用结构化面板，检测框/多边形/掩膜使用坐标一致的 Canvas/SVG 叠加层。
6. 运行与风险相称的验证，至少覆盖服务启动、核心 API、一个成功样例、一个失败样例、历史重载和批量配对边界。

## 安全边界

- 共享或暴露到不可信网络时，不允许用户提交任意模型后端 URL；使用服务端配置/允许列表，并限制重定向与内网目标，防止 SSRF。
- 校验扩展名之外还要检查 MIME/文件签名、空文件和解码结果；设置单文件、单请求、单任务和历史存储上限。
- 不把 token、内部错误堆栈或敏感原始响应返回给浏览器。多用户部署必须增加身份认证和任务所有权校验。
- 对推理 POST 仅在请求明确幂等或具有幂等键时自动重试；不要因超时盲目重复昂贵推理。

## 完成标准

交付时说明启动方式、配置入口、数据位置、已验证场景和仍存在的规模边界。不得仅凭页面能打开就宣称完成；核心推理链路尚无可访问后端时，应使用契约级 mock 验证并明确说明未做真实模型联调。
